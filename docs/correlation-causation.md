# Correlation and Causation

When one event triggers a processor which records the next event, you end up with a chain of events that belong
together. To follow such a chain later on, every message can carry two ids: a correlation id which stays the same for
the whole business transaction, and a causation id which points to the event that directly caused this message.

The library can set both ids for you, so you don't have to pass them through your domain code.

## Headers

Both ids are stored as headers on the [message](message.md) and are persisted with the event.

* `CorrelationIdHeader` - the id of the whole business transaction.
* `CausationIdHeader` - the id of the event that directly caused this message.

```php
use Patchlevel\EventSourcing\Message\Message;
use Patchlevel\EventSourcing\Store\Header\CausationIdHeader;
use Patchlevel\EventSourcing\Store\Header\CorrelationIdHeader;

/** @var Message $message */
$message->header(CorrelationIdHeader::class)->correlationId;
$message->header(CausationIdHeader::class)->causationId;
```
:::note
A message that starts a new transaction has no causation id, because nothing caused it. Its correlation id is the id of
the transaction it opens: the one generated by the command bus if you dispatch commands, the one you seeded yourself, or
as a last resort its own event id.
:::

## Message context

The ids are derived from the message which is currently being handled. The `MessageContext` holds exactly that
information and is shared between the event bus, the subscription engine, the command bus and the decorator.

```php
use Patchlevel\EventSourcing\Message\Context\MessageContext;

$messageContext = new MessageContext();
```
:::warning
Use one single instance everywhere. If you wire a second instance somewhere, the ids will not be propagated.
:::

## Enable the automatic propagation

The ids are added by the `CorrelationCausationDecorator`, which is a [message decorator](message-decorator.md).
Pass it to the `DefaultRepositoryManager` together with the shared context.

```php
use Patchlevel\EventSourcing\Message\Context\MessageContext;
use Patchlevel\EventSourcing\Metadata\AggregateRoot\AggregateRootRegistry;
use Patchlevel\EventSourcing\Repository\DefaultRepositoryManager;
use Patchlevel\EventSourcing\Repository\MessageDecorator\CorrelationCausationDecorator;
use Patchlevel\EventSourcing\Store\Store;

/**
 * @var AggregateRootRegistry $aggregateRootRegistry
 * @var Store $store
 */
$messageContext = new MessageContext();

$repositoryManager = new DefaultRepositoryManager(
    $aggregateRootRegistry,
    $store,
    null,
    null,
    new CorrelationCausationDecorator($messageContext),
);
```
:::note
If you use multiple decorators, combine them with the `ChainMessageDecorator` as described on the
[message decorator](message-decorator.md) page.
:::

The decorator only knows which message is currently being handled if the context is filled. Pass the same instance to
the [subscription engine](subscription.md), so that everything a processor records while handling an event inherits the
ids of that event.

```php
use Patchlevel\EventSourcing\Message\Context\MessageContext;
use Patchlevel\EventSourcing\Subscription\Engine\DefaultSubscriptionEngine;
use Patchlevel\EventSourcing\Subscription\Engine\MessageLoader;
use Patchlevel\EventSourcing\Subscription\Store\SubscriptionStore;
use Patchlevel\EventSourcing\Subscription\Subscriber\SubscriberAccessorRepository;

/**
 * @var MessageLoader $messageLoader
 * @var SubscriptionStore $subscriptionStore
 * @var SubscriberAccessorRepository $subscriberRepository
 * @var MessageContext $messageContext
 */
$engine = new DefaultSubscriptionEngine(
    $messageLoader,
    $subscriptionStore,
    $subscriberRepository,
    messageContext: $messageContext,
);
```
If you dispatch events synchronously over the [event bus](event-bus.md), pass the context to the consumer as well.

```php
use Patchlevel\EventSourcing\EventBus\DefaultConsumer;
use Patchlevel\EventSourcing\Message\Context\MessageContext;

/** @var MessageContext $messageContext */
$consumer = DefaultConsumer::create([], $messageContext);
```
## Correlate a whole command

A command handler often records more than one event. All of these events belong to the same transaction, so they should
share one correlation id. The `SyncCommandBus` takes care of this if you pass the context to it.

```php
use Patchlevel\EventSourcing\CommandBus\HandlerProvider;
use Patchlevel\EventSourcing\CommandBus\SyncCommandBus;
use Patchlevel\EventSourcing\Message\Context\MessageContext;

/**
 * @var HandlerProvider $handlerProvider
 * @var MessageContext $messageContext
 */
$commandBus = new SyncCommandBus($handlerProvider, null, $messageContext);
```
:::success
The bus generates a fresh correlation id for every dispatch, unless the context already holds one. Nested dispatches and
commands dispatched from a processor therefore keep the correlation id of the transaction they belong to.
:::

## Set the ids yourself

Sometimes the transaction starts outside of the library, for example with an http request. You can push your own ids
onto the context and remove them afterwards.

```php
use Patchlevel\EventSourcing\Message\Context\MessageContext;

/** @var MessageContext $messageContext */
$messageContext->push(correlationId: $request->headers->get('X-Request-Id'));

try {
    $repository->save($profile);
} finally {
    $messageContext->pop();
}
```
:::warning
Every `push` needs a matching `pop`, otherwise the ids leak into the next transaction. Always pop in a `finally` block.
:::

You can also set the headers directly on a message in your own [message decorator](message-decorator.md). Headers that
are already set are never overwritten by the `CorrelationCausationDecorator`.

## Limitations

The ids are added when an aggregate is saved over a repository. Events which are written directly with `Store::save`
bypass the decorator and therefore get no ids.

Events recorded before the decorator was enabled have no correlation id. Such an event is treated as the root of its own
correlation: everything caused by it gets the event id of that event as correlation id. The old event itself is not
changed.

:::warning
The ids are only available while a subscribe method runs. Everything the subscription engine does around a message, the
flush method of a [batchable subscriber](subscription.md) and the failure hooks, is not caused by one single message, so
writes made there get no ids automatically. A batch flush covers many messages, no matter which one happened to trigger
it. If you need ids in those places, read them from the `Message` inside the subscriber and set the headers yourself.
:::

:::note
The `MessageContext` is a stack per process and is not fiber aware. If you process messages concurrently in fibers, for
example with Swoole or ReactPHP, the frames of the different fibers interleave.
:::
